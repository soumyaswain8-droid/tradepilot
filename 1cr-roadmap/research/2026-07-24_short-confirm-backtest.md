# Short-Confirmation Hard Gate — Retroactive Backtest

> Author: Soumya Swain <soumya@suryaai.co.in>. Read-only analysis; no engine
> or scorer code was modified. Backtests approach (a) from
> `1cr-roadmap/research/2026-07-21_sell-tier-scorer-gap.md` §3 against the actual
> `docs/audit/*_trade-audit.jsonl` + `docs/paper-trades/{v5,v5_classic}/*.json`
> trade history, base commit `7e121e6`.

## Verdict

None of the three gate variants comes close to matching the audit's
"Rs 3.0–3.2k/day SHORTED_RISER cost" framing as a same-magnitude *savings*
number — and that comparison is itself apples-to-oranges (see caveat 3).
Measured on realized P&L only, over the trades where each rule is actually
evaluable:

| Variant | Rule | Net savings (window total) | Net savings/eligible-day | SHORTED_RISER caught |
|---|---|---:|---:|---:|
| A — red-day-only (proxy) | block if day return ≥ 0 | **+Rs 3,592** | ~Rs 359/day (10 d) | 42/255 (16%) |
| B — below-VWAP-only (recorded) | block if above VWAP at entry | **−Rs 742** (net loss) | ~Rs −62/day (12 d) | 11/279 (4%) |
| C — AND-gate (recommended, = design doc's approach (a)) | block unless red AND below VWAP | **+Rs 1,859** | ~Rs 186/day (10 d) | 46/230 (20%) |

**Recommendation stands directionally — ship the AND-gate, not either leg
alone** — but the backtested effect size is far smaller than the "Rs
3k/day" headline suggests, and Variant B in isolation is net *negative*
(it blocks more good shorts than bad ones). See §4 for why, and §5 for the
exact code insertion point.

## 1. What data exists, honestly

- **`docs/audit/*_trade-audit.jsonl`** (one row/trade): `symbol`, `side`,
  `entry_price`, `exit_price`, `entry_time`, `exit_time`, `actual_pnl`,
  `score`, `stock_day_return_pct` (yfinance close-vs-prev-close, i.e.
  **full-day, close-based** — not an at-entry reading), `mistake_class`
  (incl. `SHORTED_RISER`), `status`. No `change_pct`-at-entry, no VWAP
  field. Generated by `scripts/trade-audit.py` (`audit_trade()`,
  lines 213–283) — `SHORTED_RISER` there is computed from the trade's own
  `exit_price - entry_price` (line ~257), not from `stock_day_return_pct`,
  so the mistake-class label itself is entry/exit-price-based and trustworthy.
- **`docs/paper-trades/{v5,v5_classic}/YYYY-MM-DD.json`** → `pools.INTRADAY.closed[]`:
  same trades, plus a free-text `reasons` list generated by
  `prototype/v4/composite_scorer.py:_build_reasons()`. Two of those lines are
  load-bearing: `"Price +X% above VWAP (vwap)"` (printed whenever
  `vwap.above_vwap` is `True`) and `"Price X% below VWAP (vwap)"` (printed
  only when `price_vs_vwap_pct < -0.2`). Every closed SHORT in the window
  matched 1:1 to a `reasons` record by `(symbol, entry_time, exit_time,
  entry_price)` — **0 unmatched out of 678**.
- **What is NOT reconstructable without network calls**: an at-entry
  `change_pct` (intraday change at the scan instant). The `reasons` text only
  surfaces a change-based line ("Sharp fall X%") when `change_pct < -2.0%`
  (`composite_scorer.py:256`) — a narrow trigger that most trades don't hit,
  so it can't be used as a general red/green signal. The only day-direction
  field present for (most) trades is `stock_day_return_pct`, which is
  **close-based**, not entry-time — this is the proxy, labeled honestly
  throughout as Variant A.

So: **VWAP is recorded, not proxied** (89% coverage via the `reasons` text,
because `above_vwap` is a clean boolean upstream and both branches of its
`if/elif` are mutually exclusive with "no line" only when neither VWAP
condition fires strongly). **Red-day is a proxy** (close-based day return
sign, not the at-entry reading the live gate would actually see) — labeled
as such everywhere below.

## 2. Backtest window

12 trading days with audit files since 2026-07-06: 07-06, 07-07, 07-09,
07-13, 07-14, 07-15, 07-16, 07-17, 07-20, 07-21, 07-22, 07-23 (07-08 and
07-10 skipped — outage days per `MEMORY.md`). 678 closed SHORT trades across
v5 + v5_classic (306 of them `SHORTED_RISER`, 45% of all closed shorts in
the window). `stock_day_return_pct` is `null` for **all** shorts on 07-21
and 07-22 (yfinance OHLC fetch gap that day, per `trade-audit.py`'s
`--no-fetch` fallback) — Variant A and C are simply not evaluable those two
days and are excluded from their totals rather than guessed.

## 4. Why the effect is smaller than "Rs 3k/day"

1. **The audit's "Est. cost if avoided" column is not what a no-trade gate
   recovers.** `trade-audit.py`'s `rs_on_table` for a `SHORTED_RISER` trade
   is the *flip-to-opposite-side* counterfactual (`opposite_pnl = -actual`,
   line ~245), i.e. roughly **2x the realized loss** — it assumes the
   engine had gone LONG instead, not that it simply hadn't traded. A hard
   gate that blocks the short (rather than flipping it to long) can only
   ever recover the **realized loss**, not the doubled "cost if avoided"
   figure the audit reports quote. The realized-loss-only numbers for the
   three most recent audits are Rs −1,944 (07-21), −1,318 (07-22), −1,590
   (07-23) — already roughly half the quoted "Rs 3.0–3.2k/day" before any
   gate is even applied.
2. **Most SHORTED_RISER trades are already below VWAP at entry** (577/678
   closed shorts in the window, 85%) — `score_for_short()`'s existing soft
   weighting already biases entries toward below-VWAP names even without a
   hard gate, so the VWAP leg alone has little left to catch (only 27
   above-VWAP entries exist to block, and blocking them costs more in
   forgone winners than it saves — Variant B nets negative).
3. **The short book is net profitable overall in this window** (all 678
   closed shorts sum to **+Rs 8,601**, not a loss) — `SHORTED_RISER`
   trades are real, recorded, and cost money on the days they fire, but
   other short trades in the same window offset them. The 15%-of-candidates
   pass bar proposed in the design doc's Gate-1 plan (§4) is not met by any
   variant here: even Variant C only catches 20% of the SHORTED_RISER
   trades it can evaluate, leaving 80% (184/230 evaluable) untouched by
   this specific gate — those are cases where the stock was both red and
   below VWAP at entry and still rallied through the stop.

## 5. Honest caveats

- **Proxy quality (red-day).** `stock_day_return_pct` is close-vs-prev-close,
  computed after the fact from yfinance daily bars — it is not what the live
  `signal_engine.py` gate would see at the scan instant (`change_pct` is
  the correct live field per §3 of the design doc, and it is not persisted
  anywhere in this repo's on-disk history). A stock can be red at 09:50
  entry and green by close, or vice versa; Variant A's blocked/kept split is
  therefore an approximation of what the live gate would do, not a replay
  of it. Flagged in every table above as "proxy."
- **VWAP recorded, but with an ambiguous middle band.** The "below VWAP"
  reason line only prints when `price_vs_vwap_pct < -0.2` — trades sitting
  between −0.2% and 0% below VWAP produce **no** reason line and are
  bucketed "unknown" (74/678, 11%), indistinguishable from missing
  intraday data entirely (the same default `above_vwap=False,
  price_vs_vwap_pct=0.0` fires when the VWAP feature computation has no
  data). Both variants exclude "unknown" rather than guess a direction.
- **Survivorship of what's recorded.** Only *closed* SHORT trades are in
  scope (`status == "closed"`); any SHORT still open at audit time, or any
  candidate the engine's *existing* Fix #1 gate already filtered out before
  it became a trade, is invisible to this backtest by construction — this
  measures the marginal effect of a *tighter* gate on trades that already
  passed the current one, not the gate's effect on the full candidate pool.
- **Double-count / capital reuse (unmodeled).** Blocking 27–65 short entries
  per variant frees INTRADAY-pool capital and position slots that the
  engine would, in the live system, likely deploy into the next-ranked
  candidate instead of sitting in cash. This backtest treats blocked
  capital as idle (a "no trade" gate), which is the conservative
  read for savings but is not literally what would happen — the freed
  slots' next-best-use P&L is not modeled and could move the net savings
  numbers in either direction. Flagged as an open question, not estimated.
- **07-21/07-22 OHLC gap.** All 116 shorts across those two days have
  `stock_day_return_pct: null` — Variant A/C results are silently missing
  ~17% of the window's trade volume rather than including a guessed value.

## 6. Recommended rule + exact insertion point

**Ship Variant C (AND-gate)**, matching design doc §3 approach (a) — it is
the only variant that is both net-positive on realized P&L *and* improves
SHORTED_RISER capture rate (20% vs. B's 4%), even though the absolute
Rupee impact (~Rs 186/eligible-day) is much smaller than the audit's
headline "Rs 3k/day" framing once caveat 4.1 is accounted for.

**Do not ship Variant B alone** — the backtest shows it net-loses money
(forgone winners > avoided losers, 15 vs 12 trades) because most shorts are
already below VWAP by construction of the existing soft weighting (§4.2);
a hard VWAP-only gate has few true positives left to catch and mostly just
blocks legitimate above-VWAP-but-still-weak shorts.

**Thresholds to use** (same as the design doc's approach (a), unchanged from
what's already live): `change_pct < 0` (strictly red on the day, replacing
today's looser `-0.5%` bar with a stricter zero-bound per the audit's
literal "never short a stock that's green on the day" prescription) **AND**
`not above_vwap` (i.e. `below_vwap` from `score_for_short()`).

**Exact insertion point — do not edit, cited for the implementer**:
`prototype/v5/signal_engine.py`, inside the `actually_weak` gate at
**lines 196–199**:

```python
stock_change = stock.get("change_pct", 0)
stock_score = stock.get("score", 100)
actually_weak = (stock_change < SHORT_REQUIRE_NEGATIVE_CHANGE_PCT and
                 stock_score < SHORT_REQUIRE_MAX_SCORE)
```

`score_for_short()` (lines 56–87) already computes `below_vwap` at line 68,
but today it is only called *after* `actually_weak` passes (line 202) — to
make VWAP a hard AND term, the VWAP position needs to be computed (or
looked up from `stock`, if `v4.composite_scorer` already attaches
`above_vwap`/`price_vs_vwap_pct` to the per-stock dict upstream — not
verified in this pass, flagged as a pre-implementation check) **before**
line 198, and the `actually_weak` boolean extended with `and not
stock_above_vwap`. This keeps the existing `SHORT_REQUIRE_NEGATIVE_CHANGE_PCT`
/ `SHORT_REQUIRE_MAX_SCORE` env-tunable pair intact per design doc §6
open-question 4's lean (keep both, don't collapse into VWAP alone — this
backtest's Variant A vs. B results independently support that lean: A and
B block almost entirely different trades — A's 46 blocks are dominated by
"not red" and B's 27 blocks are entirely "above VWAP", with only a small
overlap population — so the two conditions are catching different mis-short
cases, not the same one twice, on their own eligible-trade sets).
