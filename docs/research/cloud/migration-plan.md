# TradePilot: Mac → Linux Cloud VM Migration Plan

**Headline risk:** two hosts each hold their own `flock` on `docs/sarathi/knowledge/floor.lock` (`prototype/agents/floor.py:1011`), so the single-instance guard that was written *specifically* to stop the 2026-08-28 double-book corruption is silently void the moment a second machine runs the floor — the 08-28 failure at two-host scale, with no detector that fires.

**Recommended sequence:** move the 24/7 collectors first, then the read-only Flask terminal, then the batch/EOD jobs, and move the floor **last and only as a hard cutover** — never in parallel — with the Mac authoritative until each phase has produced byte-identical artifacts for five consecutive sessions.

## 1. Scheduler translation

### Recommendation: **systemd user units + timers**, with `loginctl enable-linger`.

Justification, against the alternatives:

- **cron** loses everything that matters here. No per-job log capture (the plists set `StandardOutPath`/`StandardErrorPath`), no dependency ordering, no `Persistent=` catch-up, no restart policy, and no equivalent of `launchctl kickstart -k` — which `scripts/floor-watchdog.sh:131` depends on structurally, not incidentally. Cron would force a rewrite of the watchdog's restart path into exactly the `nohup` pattern that the file's own comment block (lines 119–126) records as having lost 2h40m of a session.
- **A supervisor (supervisord / pm2)** handles the one long-running job well and the other 40 badly. It has no calendar scheduling; you would end up running cron *inside* supervisor and get the worst of both.
- **systemd** maps every idiom in use natively, and is the only option that preserves the watchdog's "restart a job that the init system owns, independently of my own process" semantics.

**User units, not system units**, because: the migration is 1:1 with LaunchAgents (also per-user), it avoids `sudo` in the restart path, and `~/.config/systemd/user/` can be a symlink into the repo so the definitions become versioned — fixing the "34 job definitions exist in one place outside git" problem in the same move. `loginctl enable-linger <user>` is required or the units die at logout.

### 1.1 Process lifecycle: what actually changes

Three mechanisms in this repo are load-bearing on launchd's specific reaping behaviour. All three change.

**(a) The flock survives the move; its *scope* does not.**
`prototype/agents/floor.py:1038-1048` uses `fcntl.flock(LOCK_EX|LOCK_NB)`. This is POSIX and behaves identically on Linux — *on one host*. Two facts to hold:
- `flock` on Linux over **NFS** is emulated via POSIX locks in modern kernels but has historically been a no-op or silently local; over **overlayfs inside a container** it locks the container's own layer. If any part of the migration puts `docs/sarathi/knowledge/` on a network or shared mount, verify the lock empirically before trusting it. I have not verified which filesystem the target VM will use — this is an explicit test, not an assumption.
- Even with perfect local semantics, **Mac and VM each acquire their own lock**. The guard has no cross-host dimension. This is the headline risk and §5 is built around it.

**(b) The watchdog's restart path improves, and its fallback gets worse.**
`scripts/floor-watchdog.sh:131` — `launchctl kickstart -k gui/$(id -u)/com.tradepilot.agent-floor` → `systemctl --user restart tradepilot-floor.service`. This is a genuinely clean 1:1: systemd owns the unit independently of the watchdog process, which is exactly the property lines 119–130 argue for.

The `setsid` fallback at line 135 is the one that regresses. On macOS, launchd reaps the job's process *group*, and `setsid` escapes it — which is why the fallback works today. **systemd kills by cgroup, and `setsid` does not escape a cgroup.** With the default `KillMode=control-group`, a `setsid`'d child of a `oneshot` watchdog unit is killed the instant the watchdog exits — a guaranteed-dead fallback that would report success. Either drop the fallback, or replace it with `systemd-run --user --scope`, which places the child in its own transient cgroup. Leaving line 135 as-is is worse than having no fallback, because it will log `"fell back to setsid"` and the floor will be gone.

**(c) The tick-counter duplicate detector still works and must stay.**
`scripts/floor-watchdog.sh:94-99` detects a decreasing tick counter and refuses to restart. Under systemd this remains the only detector that would catch a two-host double-write *if both hosts append to the same log path*. In practice they will not (separate filesystems), which is precisely why §5 forbids parallel floors rather than relying on this.

**(d) Do not add `Restart=always` to the floor.** It is tempting because systemd offers it. It would recreate the 08-28 amplification loop: crash-on-startup becomes an unbounded respawn, and the `MAX_RESTARTS=4` cap at `scripts/floor-watchdog.sh:30` — a deliberate guard — would be bypassed entirely. Keep restart decisions in the watchdog where the cap and the duplicate detector live.

## 2. Timezone

IST has no DST, so `Asia/Kolkata` is a fixed UTC+05:30. That makes this tractable — but a UTC box shifts **every** wall-clock assumption by 5h30m, and almost all of them fail silently rather than loudly.

### Must be set

1. `sudo timedatectl set-timezone Asia/Kolkata` — the box's system timezone. This is the single highest-leverage action and it fixes the large majority of the surface below in one move.
2. `Environment="TZ=Asia/Kolkata"` on every unit, as belt-and-braces. Units inherit the system TZ, but a container or an `su`-style invocation may not.
3. If you choose per-unit calendars in a different zone instead: systemd supports a timezone suffix on `OnCalendar` (e.g. `Mon..Fri 09:15 Asia/Kolkata`) only in **recent** systemd. I believe this landed around v252 but have **not verified the exact version** — check `systemctl --version` on the target before relying on it. Setting the system TZ avoids the question entirely; do that.

### Must be audited

| Surface | Where | Failure mode if TZ is wrong |
|:--|:--|:--|
| **600 naive `datetime.now()` calls** across `prototype/` and `scripts/` | measured count, e.g. `floor.py:230, 310, 599, 604, 628, 741, 756, 873, 978` | The largest surface by far. `floor.py:599` and `:604` compare `datetime.now().strftime("%H:%M")` against `"15:30"` for the force-exit and session-end. On a UTC box the floor started at 09:16 IST would think it is 03:46 and **never exit** — running past the close, holding positions overnight, writing tomorrow-dated files. |
| **Date-stamped output filenames** | `floor.py:756` (shadow ledger), `:873` (positions), `:978`/`:985` (escalations) | Files land under the wrong date. Because they are `%Y-%m-%d` from a naive `now()`, everything from 18:30 IST onward would be stamped as the *previous* day on a UTC box — silently interleaving two sessions in one file. |

It is luck, not design. `scripts/auto-stop-eod.sh:100-120` uses the same idiom at times that do straddle. |
| **`date` in log filenames** | `floor-watchdog.sh:21`, `run-lane.sh:15`, `crash-watchdog.sh:36`, `launch-market.sh:57`, `post-open-check.sh:36`, `.claude/team/cadence/nightly-backup.sh:20`, plus every `>> logs/<n>-$(date +%F).log` plist wrapper | Watchdog writes to `logs/floor-watchdog-<wrong-date>.log` while the floor writes to `logs/agent-floor-<other-date>.log` → the watchdog reads an empty/absent log, concludes DEAD, and restarts a healthy floor. They are correct and would stay correct under any box TZ. |

### Audit procedure

Set the box to `Asia/Kolkata` **first**, then run the whole fleet for a week and diff artifacts against the Mac. Do **not** attempt to make 600 `datetime.now()` calls timezone-aware as part of this migration — that is a separate, larger, riskier change. The correct migration-time posture is: *make the environment match the code's assumption*, and add one startup assertion.

Suggested guard (a proposal, not yet written): a check in `prototype/envcfg.py` that refuses to start any engine if `time.tzname` is not IST / `datetime.now().utcoffset()`-equivalent is not +05:30. One line, fails loudly, covers all 600 sites.

### Does git-as-durability still work unattended?

**Mostly yes, with three caveats that must be closed before the box is left alone.**

1. **Auth.** `eod-git-commit.sh:42` does `git push origin dev` with no credential handling. On the Mac this rides the Keychain. On a VM it needs a deploy key (`ssh-agent` is not present in a systemd `oneshot` unit — use `GIT_SSH_COMMAND` with an explicit `-i`, or a credential helper). Without this the job fails every day and the only symptom is `exit 1` in journald.
2. **Silent divergence.** `:45-47` already handles a diverged `main` by warning rather than forcing — good, and correct to keep. But nothing *pages* on that warning. Unattended, a diverged main degrades quietly for weeks. Route this to the existing Telegram channel.
3. **The mid-session gap.** The EOD commit fires at 17:30 (`v2.eod-git-commit`), well after the 15:30 close, so a normal day is safe. But between 09:15 and 17:30 the live book exists only on the VM's disk. **Git is an EOD durability layer, not a continuous one.** For an unattended box that is a real exposure the Mac did not have (the Mac was in the room).

**Recommendation:** do not try to make git continuous — committing mutable state every N minutes would produce a useless history and fight the deliberate `--others` design. Instead: hourly `rsync`/snapshot of `docs/sarathi/knowledge/` + `docs/paper-trades/` to object storage (S3/B2) with versioning on, keyed by date. Cheap, out-of-band, and orthogonal to git. Keep the EOD commit exactly as it is.

### Restore

A restore must produce a working box from: **(1)** the git repo, **(2)** the `.env` from a password manager / secrets store, **(3)** the latest object-storage snapshot of the two state directories, **(4)** `python3 quant/bars.py --build` to regenerate the bhavcopy parquet.

**Verified:** `quant/bars.py:169-170` routes `--build` to `build_cache()`, which consolidates `quant/data/bhavcopy/` (`:42`) into `bhavcopy_daily.parquet` (`:43`) and raises `FileNotFoundError` if that directory is empty (`:65`). So `--build` regenerates the 60 MB parquet **but not the 381 MB of raw CSV inputs it reads**. Those must be in object storage, or re-fetched from NSE (slow, rate-limited, 1,300+ files). Treat `quant/data/` as a one-time 621 MB seed upload, not a rebuild.

**The restore must be rehearsed once, from scratch, into a throwaway VM, before the Mac is stood down.** An unrehearsed restore is not a durability plan.

## 5. Migration sequence

The governing constraint: **the Mac stays authoritative until each piece is proven, and the floor is never run on two hosts at once.**

### Phase 0 — Preconditions (before any VM exists)

1. Recover the 3 out-of-repo scripts from `~/Library/Application Support/tradepilot/` into `scripts/external/` and commit. Reconcile the diverged `eod-comparison-daily.py`.
2. Export all 41 plists into the repo (they are the only spec for ~34 jobs). Even as raw XML, versioned, before rewriting.
3. Upload `quant/data/` (621 MB) to object storage.
4. Write the systemd unit set generated from the plists — but do not enable anything.
5. Provision `.env` into a secrets store.

### Phase 1 — 24/7 collectors (lowest risk, no market-hours coupling)

Move: `news-watch` (P4). Optionally `v2.bk-daily` (P6).

`news-watch` is the ideal first mover: it is 24/7, and its ledger is append-only and content-hash deduplicated — `scripts/news-watch.py:280` keys on `sha1(title.lower())[:16]`, `:238-245` loads the day's existing hashes, `:320` appends. Verified, not assumed.

**Duplicate-safety — with one real caveat.** Content dedupe means two hosts cannot produce contradictory *rows*. But the dedupe set is scoped to a per-day file (`:253-254`), so each host only sees its own. Merging the two ledgers later dedupes cleanly on `hash` — except for `first_seen_utc` (`:302`), which the module's own docstring at `:17` calls *"this file's whole point"*. A naive merge keeps an arbitrary host's timestamp; the meaningful value is the **earliest**. So: parallel running is safe, but the merge must be `min(first_seen_utc)` per hash, not first-writer-wins. If you would rather not write that merge, run the parallel week with the VM writing to a *separate* directory and diff, rather than merging at all.

Exit criterion: 5 consecutive days of VM output matching the Mac's, then disable on the Mac.

### Phase 2 — Read-only web tier

Move: `prototype/app.py` behind nginx + TLS + auth.

Serve it **read-only** from the VM, pointed at state that is still written by the Mac (synced one-way, Mac → VM). This proves the network, the TLS, the reverse-proxy `remote_addr` handling (§3 #23), and the terminal's warm-up behaviour, while the Mac remains the sole writer.

**Before exposing:** fix `app.py:3613` — the credential-writing endpoint whose only access control is the loopback bind. Either remove it, or put it behind real auth. This is a hard gate, not a nice-to-have.

Run both. Two Flask instances reading the same state is harmless.

### Phase 3 — Batch and EOD jobs

Move: P1, P2, P3, P6 (38 jobs), **excluding** anything that writes the live book.

Split them by write target:
- **Read-only / report-generating** (`v2.standup`, `v2.fleet-telegram`, `engine-compare`, `weekly-tracker`, the three `due-*`, `dqo-*`, `guard-*`, `preflight`) → safe to run on both, diff the outputs.
- **Artifact-writing** (`v2.exec-eod`, `eod-comparison-daily`, `us-*`) → run on VM, keep Mac's as the reference, diff, then disable the Mac's.
- **`v2.eod-git-commit` must run on exactly one host, ever.** Two hosts committing date-stamped artifacts to the same branch produce push races and, worse, two different versions of the same day. Move it last within this phase, as a hard cutover on a single day.
- **The lanes** (`lane-real`, `lane-opt`, `lane-sarathi`, `lane-squareoff`, `tokencheck`, `shadow-settle`) write the small-capital books. `scripts/run-lane.sh:13` defaults `LANE_MODE=paper` — but the file's own header says it flips to `real`. **These are hard cutover, not parallel**, for the same reason as the floor.

### Phase 4 — The floor (hard cutover, single day, supervised)

This is the one that cannot be run in parallel, and the reason is mechanical, not cautious: `floor.py:1011`'s flock is per-host. Two floors on two boxes both acquire cleanly, both stream, both write `docs/sarathi/knowledge/positions/<date>.json` and `shadow/<date>.jsonl`. If those directories are ever synced or merged, you reproduce 2026-08-28 exactly — "44 closed trades at 11:36 became 5 by the close" — with the additional cruelty that the tick-counter detector at `floor-watchdog.sh:94` cannot fire, because the two floors write to *different log files on different machines*. **The one detector that caught it last time is blind to this case.**

Procedure:
1. Pick a day. Confirm the VM's `timedatectl` reads `Asia/Kolkata` and that `date` matches the Mac to the second.
2. **Do not load** `com.tradepilot.agent-floor` or `com.tradepilot.floor-watchdog` on the Mac that morning — `launchctl bootout` them the night before, and verify with `launchctl list | grep agent-floor` returning nothing.
3. Start the floor on the VM only. Watch the tick counter live.
4. Keep the Mac powered and the repo intact as a rollback, but with the floor units unloaded — not merely "not started".

**Add a cross-host interlock before this phase.** A proposal, not yet implemented: have `acquire_single_instance()` also write a hostname+timestamp lease into `docs/sarathi/knowledge/floor.lease` and refuse to start if a *different* hostname holds a lease younger than ~120s. It is weaker than a real distributed lock and it is not sufficient on its own — but it converts a silent catastrophe into a loud refusal, which is the entire value. The strong version is a lock in something that is actually shared (Postgres advisory lock, or an S3 conditional put); worth doing if the two hosts will ever overlap for more than one cutover day.

### Phase 5 — Decommission

Only after 10+ clean sessions: unload the remaining Mac units, keep the repo and `.env` as cold rollback for a month.

## 6. What should not move

Honest arguments for leaving things on the Mac.

1. **`scripts/preopen-ingest.py:68` — the pre-open CSV ingest.** It globs `/Users/soumyaswain/Downloads/MW-Pre-Open-Market-*.csv`: a file a human downloads from the NSE website into a Mac Downloads folder. There is no headless equivalent that is not a scraper, and NSE actively fights scrapers. Either keep `preopen-fetch` on the Mac and sync the CSV up, or replace the input with a Kite/API source — a real piece of work, not a migration step. **Do not pretend this job ports.**

2. **The daily Kite token.** `scripts/kite-token-reminder.py:5` states it plainly: Zerodha invalidates `access_token` at 06:00 daily, and the replacement comes from an interactive browser login that exchanges a `request_token`. Three of the 41 jobs (`kite-token-morning` 06:05, `kite-token-preflight` 08:50, `kite-token-lastcall` 09:10) exist solely to nag a human through it. **An unattended VM cannot refresh this token.** The whole live-data path is gated on a manual human action every morning. This is the single largest obstacle to genuine unattendedness and the migration does not solve it — it makes it worse, by removing the machine the human is already sitting at. Options: keep the token refresh on the Mac and push the token to the VM; or automate the login (TOTP-based flows exist and are against Zerodha's terms — say so out loud before choosing it). Decide this **before** Phase 4, not during.

3. **The PDF/report pipeline** (10 `pyppeteer` scripts, §3 #20/#21). These are human-facing artifacts that end with `subprocess.run(["open", pdf])` — the point is that a PDF appears on Soumya's screen. Porting them means installing Chromium on the VM, rendering there, and then transferring the file to the Mac to look at it. That is strictly more machinery for the same outcome. **Leave the render scripts on the Mac**, reading state synced down from the VM. `v2.fleet-telegram` is the exception — it delivers to Telegram, not to a screen, so it should move (and needs the Chromium fix).

4. **`scripts/wifi-watchdog.sh` and `scripts/net-exposure-watcher.sh`.** Both solve problems that are artifacts of running a trading system on a laptop on untrusted WiFi. On a VM with a stable NIC and a cloud firewall, neither has a job. Retire, do not port. (`net-exposure-watcher` would need a real rewrite anyway — §3 #16.)

5. **`scripts/launch-market.sh` / `com.soumya.tradepilot-launch` / `caffeinate` / `laptop-heartbeat.sh` / `crash-watchdog.sh`.** This whole cluster exists to keep a *laptop* alive through a session — lid state, sleep prevention, heartbeat files. On a VM, systemd is the supervisor and the layer is redundant. Porting it would mean maintaining two overlapping supervision systems, which is how the 08-28 restart storm got its amplification in the first place. **Delete rather than translate.**

6. **The Flutter app build** (`app/ios/`). iOS cannot be built on Linux. Non-negotiable; stays.

7. **Development itself.** The VM should run the fleet, not be where code is written. Keeping the Mac as the dev box preserves the fast local iteration loop and, more importantly, keeps a full working copy of the system on hardware you control — which is what makes the Phase 5 rollback real rather than theoretical.
